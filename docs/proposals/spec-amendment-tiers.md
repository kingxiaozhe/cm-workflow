# 规格补正分级批准

状态：已实现（`runtime/js/cm-ai/spec-amendment.mjs`、`scripts/cm-spec-amend.mjs`）；Codex（gpt-6.1-sol high）四轮审查，第 4 轮 approved。

## 问题

开发中途每改一次规格，CM 都把批准作废，要用户本人再回「开始」。

依据：2026-11-03 至 11-04 两个会话，共 17 次「开始」，16 次因改规格。

| 会话 | 「开始」次数 | 因改规格 |
| ---- | ---- | ---- |
| wue `76c1afb5` | 5 | 5 |
| aihot-dev `0e1fcd44` | 12 | 11 |

现行规则出处：`skills/cm-prd/references/change-mode.md` 末尾「审批位重置」；
`runtime/js/cm-ai/cm-ai-admission.mjs` 的 `admissionFor`（`awaiting_review` 或 manifest 不符即停）。

## 16 次改规格的分类

| 类别 | 例子 | 次数 | 真需要用户吗 |
| ---- | ---- | ---- | ---- |
| A 机械修正 | 说明写进了「范围」行；范围路径根目录写错 | 2 | 不需要 |
| B 执行内补漏 | 测试文件补进任务范围；为已有验收标准补修复任务；拆文件；拆检查分工 | 9 | 不需要，事后知道即可 |
| C 产品决定 | 首次批准；新功能；确认设计稿；改视觉基准；删接口别名 | 5 | 需要 |

结论：约 11 次可以不停。

## 方案：三级

### 0 级：只追加版本记录，自动生效

条件：只有 tasks.md 变了，且只是在标题含「版本」的表格里追加了行（空行不计）。

动作：重算 manifest，记入快照的补正记录，不停。说明或范围的任何改写都算 1 级。

### 1 级：执行内补正，Codex 审过即生效

条件全部满足（机器判定，不靠模型自报）：

- `requirements.md` 未变；
- `design.md` 未变；
- `test-cases.json` 只新增用例；已有用例和文件头部逐字不变；
- `tasks.md` 已完成任务逐字不变；
- `tasks.md` 只允许三种变化：新增任务、扩大未完成任务的范围、拆分未完成任务；
- 新增任务必须引用已有验收标准编号；
- 本 feature 自批正 ≤3 次（第 4 次起升为 2 级）。

动作：

1. 另一个新上下文的审查者（按宿主规则，本机为 Codex）审查本次规格差异，只判「是否越出上面条件、是否削弱验收」；
2. 审查输出最后一行的 JSON 必须带本次差异摘要且判 approved，才写新 manifest；补正记录写进快照；
3. 宿主在下一条消息告诉用户改了什么，不等回复；
4. 在途运行走现有 `spec_rebind` 换绑。

### 2 级：仍要用户回「开始」

不满足 1 级的任何改动，包括：改需求或验收标准、改设计、删或弱化用例、改视觉基准、作废任务。

## 授权从哪来

首次批准时，摘要卡加一行：

> 执行中的补漏（不改需求、设计和验收标准）由 Codex 审后自动生效，你会收到通知。

用户回「开始」即同时授权 1 级。批准时加 `--no-spec-amend` 可关掉，回到现行逐次批准。

## 实现要点

- 批准时先删旧快照，再写状态，再保存 `{SPECS_DIR}/.cm-specs-approved.json` 快照（manifest 只存哈希，无法比对差异）；快照写失败时没有快照，一律 2 级；
- 快照带自身摘要，被单独改过即无效。状态为 approved 时，快照还必须等于已批准 manifest 且属于同一次人工批准（`approval.at` 相同），否则 2 级；
- 另在规格目录之外记一份批准台账：`${CM_WORKFLOW_HOME:-~/.cm-workflow}/spec-approvals/{规格目录路径哈希}.json`，记最近一次批准轮次与当前快照字节的哈希。人工批准和换绑都先作废它，全部写完才重写；中途失败就没有台账，一律 2 级。恢复规格目录的旧备份或 git 旧版本时，旧快照与台账不符，一律 2 级；
- 已知缺口：有人同时改回规格目录和用户目录下的台账时识别不出，保障级别同 `.cm-specs-status` 本身；
- 人工批准与补正换绑共用 `{SPECS_DIR}/.cm-specs-approval.lock`。人工批准在锁内重查状态字节和准入结果，期间已有别的批准落盘就拒绝；换绑在状态改名前再核对状态、快照、轮次文件和规格字节，cm-prd 并发写入时拒绝；
- `prepare` 的审查副本取自分级时冻结的同一份字节；另把涉及 feature 中未改动的规格文件放进 `context/` 供对照（实跑教训：wue v4 补正是让任务对齐设计，审查者看不到设计就判断不了）；
- `scripts/cm-spec-amend.mjs`：`inspect` 只读分级，`prepare` 写出批准时/现在两份副本和审查提示，`apply` 换绑；
- 换绑时先写 `.cm-specs-status` 再写快照；快照写失败时两者不符，下次自动退回 2 级；
- 只改 cm-ai 一侧（N1、js-host、准入）。cm-prd 的「审批位重置」不动，按流程隔离原则由 cm-ai 读取它落盘的 `awaiting_review` 后再分级；
- 夹具 `scripts/cm-spec-amend.test.mjs`：每个 1 级条件各一条「越界即升 2 级」的反例。

## 不在本方案内

- 批准口令仍只认「开始」，不放宽「可以」；
- 在本功能上线前批准的规格没有快照，下一次补正仍要回一次「开始」；
- 审查两轮上限、重开只许一条旧运行等工具自身卡点，另行处理。
