AI 自动开发流水线

规格驱动的自动化开发工作流（cm 工作流） · 实现机制与投产路径

把需求文档丢进去，AI 自动拆成规格和任务清单，逐个开发、双重代码审查、动态触发测试、自动同步文档，全程状态落盘、可断点续跑、可审计。人只做两件事：审需求规格、拍业务决策。

01为什么做

直接让 AI 写代码，项目一大就失控：上下文装不下全部需求、会话中断即前功尽弃、质量无人把关、需求一变容易推翻已完成的工作。业界今年的共识方向是「规格驱动开发」（AWS Kiro、GitHub Spec Kit、开源 OpenSpec 均属此类）。我们做的是这个方向上执行管控更严、可直接对接自己研发流程的一套实现：基于 Claude Code 原生扩展机制（命令 + 技能 + 子代理），模块设计对齐 Google 发布的 Agent 设计模式（流水线 / 审查器 / 反问器等），无自研平台负担，随官方能力升级。

02怎么工作 — 三个阶段

阶段一规格化

  • 需求文档 → 自动生成需求 / 设计 / 任务清单三件套（功能项、验收标准、任务均带编号，可追溯）
  • 产品角色执行歧义五问：有歧义、涉及支付权限等敏感点，强制停下来问人，不自行假设
  • 人审查规格后才进入开发
→

阶段二自动开发

  • 按任务清单逐个执行，按类型自动派给十一个专业角色（产品 / 金融 / 前端 / UI 还原 / 小程序 / 后端 / 数据库 / 合约 / QA / 运维 / 文档），每个 feature 以 staging 部署冒烟收尾
  • 每个任务过两道审查门禁，通过才算完成
  • 按四维风险评分动态触发 QA，高危场景无条件触发
→

阶段三收尾

  • 自动同步 README、项目规范、按日期生成变更日志
  • 文档与代码一致性校验（命令、路径、环境变量逐项比对）

03AI 实现的六个关键机制

这是本方案与"让 AI 放开跑"的本质区别 —— 每一条都针对大模型的一个已知弱点。

状态外置对抗上下文限制

所有状态落磁盘：规格三件套、任务清单勾选状态、经验库、git 提交历史。AI 的记忆随时可清空、随时可重建——这是断点恢复的根，也是天然的审计链：每个任务做了什么、为什么这么做，全部有文件可查。

上下文轮换对抗长会话漂移

每完成一个任务即清空上下文、重新加载规格。AI 永远以"新鲜大脑 + 完整规格"的状态执行下一个任务，不会因连续工作而注意力退化、偏离需求。这是拿算力成本换可靠性的核心取舍。

双模型交叉审查对抗单模型盲区

执行模型自审后，第二个模型独立复审单任务 diff，互相挑错，审查不通过不得标记完成。复审设 2 轮硬上限——AI 互审没有尽头，超限后分歧留痕分流：安全类升级人工，风格类放行。外部模型不可用时自动降级并留痕。

纪律与技术分层对抗并行失控

并行工种由预定义子代理执行：子代理只管纪律——只做指定编号任务、不碰界外文件、不自行标记完成、按固定格式汇报；技术规范由对应技能文件提供。两层分离，并行再多也不会互相踩踏。

人机决策边界对抗越权风险

写死在流程里：技术选型 AI 自主（不打扰人）；业务歧义、破坏性数据库变更、合约上线、支付 / 认证 / 权限逻辑强制暂停等人确认。每类子代理还有领域硬闸（如数据库删表必上报、合约代理不碰私钥）。

动态 QA + 量化验收对抗测试成本与主观验收

QA 按四维风险评分触发：改文案不跑全量测试，动支付必测。UI 还原不靠"看着像"，用像素级对比工具量化差异。跨仓库任务已接入官方多 agent 组队并行（实验特性，默认关闭）。

04投产路径 — 三阶段，每阶段有量化门槛

当前状态：v0.9.11。已在真实小程序项目完成 12 个 feature / 81 任务实跑（从 MVP 到提审就绪）：一次通过率 93%、审查拦截 93 条（含 P0 级 4 条，如切纸错位 39.9mm、渲染空白）、81 任务计划外人工介入 0 次；另在同项目完成存量二开实测（防护网 184 用例前后全绿，存量回归 0）。唯一待补：单任务成本实测——试点第一指标。

阶段 内容 通过门槛（试点后校准） 时间
① 试点 1 个低风险小需求（3–5 个任务），全流程走通，全程记录数据 流程无人值守跑通 · 人工介入 ≤2 次/任务（业务确认除外）· 实测单任务成本 下周
② 灰度 2–3 个真实需求，覆盖不同类型（纯前端 / 前后端联动 / 含数据库变更） 任务一次通过率 ≥80% · 上线后严重缺陷逃逸 = 0 · 单任务成本低于对应人工工时 试点后 2–3 周
③ 投产 纳入正式研发流程：规格评审并入现有需求评审，产出并入现有 CR / 提测环节 团队使用规范与培训完成 · 与现有 CI/CD 及代码评审流程对接验证 灰度达标后

距投产的已知缺口（如实列出，均有对策）：

  • 单任务成本尚未实测 —— 已实跑项目未采集费用数据（采集机制已内置于收尾节点），试点第一优先补齐。
  • 断点恢复依赖任务标记的准确性 —— 已实现"写入后立即回读校验"；灰度阶段追加 git hook 双保险。
  • 第二审查模型依赖外部 Codex —— 降级逻辑已实现：不可用时单模型审查并在记录中标注，不阻塞流程。
  • 规格质量决定产出质量 —— 无技术方案可绕过，制度保证：人审规格为强制环节，并入现有需求评审。

架构演进原则：当前执行引擎为 Markdown 状态机——人人可读、人人可改、维护门槛低。确定性更强的 JS 编排引擎已完成评估，升级点已锁定（对抗式审查验证、大并行组编排），但是否升级以试点数据为准：人工介入若都发生在业务确认上，说明现有引擎够用；若发生在"流程失守"上，才把对应节点代码化。引擎升级看失败数据，不看技术潮流。

需要的决策：① 批准试点，从近期排期指定一个低风险小需求；② 认可三阶段门槛作为推广评判标准（数字可在试点后共同校准）。

附备询要点

成本结构是什么？
主要开销两块：每任务重载规格（可靠性代价）+ 双模型审查。比对话式开发贵，换来的是无人值守与质量门禁。单任务实测成本是试点第一指标，灰度门槛要求低于对应人工工时。
AI 产出怎么审计？
全程落盘：规格三件套 + 带编号的任务清单 + 每任务的审查记录 + 经验库 + git 提交历史，形成完整证据链。任何一行代码都能回溯到对应任务和需求编号。
代码质量怎么保证？
三道防线：双模型交叉审查（只看单任务 diff，审查面可控）、风险评分触发 QA、高危操作强制人工确认。审查不通过任务不得关闭。
和直接用 Cursor / Copilot 的区别？
那些是"人驾驶、AI 辅助"，效率上限受人的带宽限制；本方案是"AI 执行、人把关"，把人的投入集中到规格和决策两个杠杆点，且过程可无人值守。
市面上已有 OpenSpec 等开源方案，为什么自己做？
方向一致，正说明选型没错——OpenSpec（Fission AI）是 spec-driven 流派的代表，和我们独立收敛到同一套规格三件套地基（requirements/design/tasks + 先规格后编码），命令结构也几乎一一对应。差别在覆盖面：OpenSpec 自划边界为"规划+实现"就停，明确不含代码审查闸门、QA、部署发布、角色分工；而这四样正是本方案面向"可投产"多做的部分——双模型审查、动态 QA、发布待决清单、11 个工种 skill+ 领域举旗。一句话：OpenSpec 相当于本方案的前三个节点，我们把流水线延伸到了上线。它成熟的 CLI 工程化与跨团队协作（Stores）是我们后续演进的现成参照，非重复造轮。
需求中途变更怎么办？
有专门的变更模式：新旧需求自动对比，任务清单增量更新（新增 / 修改 / 作废分别标记），已完成的工作不推翻，重跑自动跳过。
最大的风险是？
规格错则做得快错得也快——所以"人审规格"是制度上的强制环节；其次是任务标记单点，已有回读校验 + 灰度阶段 git hook 双保险。
为什么不直接上更强的多 agent / JS 编排引擎？
都已评估并预留了接口：组队能力已接入但默认关闭，JS 引擎的定向升级点已锁定。原则是不在拿到试点失败数据前加架构——避免为技术而技术。
AI 之间会不会互相审查到失控？
会，这是业界已知失败模式（代码被无限改写到不可维护）。所以复审设 2 轮硬上限，超限分歧留痕：安全类升级人工，风格类放行。
