QUOTE

AI 写代码的能力已经很强，但它说的“已经完成”，仍然需要证据。

不知道你用 Codex、Claude Code 写代码时，有没有遇到过这种情况。

你把需求发给它。它分析了一会儿，开始疯狂修改文件。过了十几分钟，它告诉你：

“已完成，测试通过，可以提交。”

你挺高兴。结果打开页面一看，按钮点不了。再看测试，根本没真正跑起来。换一个新会话追问，它又完全不知道上一个会话做了什么。

最让人难受的，不是 AI 不会写代码，而是你不知道它说的“完成”到底完成到了哪一步。

01

CASE STUDY

有一次，我差点把“没跑的测试”当成通过

前段时间，我让 AI 接管一个已有项目。它完成了代码扫描，也执行了一部分检查，表面上看结果不错。

但往下追才发现：依赖安装那一步就已经被构建审批卡住了，后面的正式测试命令根本没有进入测试工具。

它补跑了一些底层检查。这些检查确实通过了，但底层检查通过，不能等于项目正式命令通过。

还有一次，我让 AI 做页面测试。测试走到一半，电脑锁屏了。前面的操作有记录，后面的最终结果没有。

NOTE

如果只看聊天总结，很容易得到一句“页面基本正常”。但它可能只代表页面打开了，不代表登录成功、关键按钮点过或完整业务路径得到验证。

“基本正常”到底是什么意思？是登录成功了？页面打开了？关键按钮点过了？还是只是看见页面没报错？这些事情，如果没有证据，谁也说不清楚。

我就是从这里开始意识到：AI 写代码的能力已经很强了，但 AI 完成一项开发任务的能力，仍然需要流程约束。


02

THE PROBLEM

AI 更像一个能力很强、但非常健忘的新员工

现在很多人使用 AI 写代码，还是把任务拆成几句临时指令。

... chat

帮我实现这个功能。

帮我检查一下。

没问题就提交。

整个过程看起来很顺，但里面其实有几个问题：

需求没有真正拆清楚

AI 一边理解需求，一边自行决定方案。

缺少独立审查

写代码的人和审代码的人处于同一个上下文。

状态只存在聊天里

对话一旦中断，任务状态也跟着丢失，“看过代码”还很容易被说成“测试通过”。

这就像招了一个能力非常强的新员工。但你没有给他岗位职责，没有验收标准，没有测试流程，也没有交接文档。

最后项目出问题，不能只怪员工，流程本身就没有建立起来。


03

FIVE RULES

后来，我给 AI 定了五条规矩

我没有一开始就想做一个多 Agent 平台。我只是想让自己每天使用 Codex 和 Claude Code 时，少踩几次坑。所以我先给 AI 定了五条很简单的规矩。

第一条：不要拿到需求就开始写代码

先把需求整理成：到底要解决什么问题；准备怎么实现；会影响哪些已有功能；具体拆成哪些任务；什么结果才算完成。

这些内容先写进文件。我看过并明确确认以后，才能开始编码。普通的一句“继续”，不能算批准。

第二条：一次只完成一个明确任务

AI 很容易在实现登录功能时，顺手重构用户模块，再顺手修改权限设计。最后改动看起来很多，但没人说得清哪些是需求，哪些是临时发挥。

所以每次只做当前任务。超出范围的想法，可以记录，但不能偷偷塞进代码。

第三条：写代码的人，不能直接宣布自己审查通过

AI 自己审自己写的代码，很容易沿着原来的思路再走一遍。真正有价值的 Review，应该尽量换一个新上下文。

让另一个 Codex 子代理，或者一个隔离的只读 Codex 会话，从头检查这次修改。没有独立审查条件时，也必须明确写出来：“这次只是自审，不是独立 Review。”

第四条：测试必须区分“看代码”和“真的跑过”

我把测试分成三种：

01

看代码逻辑

能判断分支是否存在，但不能叫测试通过。

02

正式命令

运行单元测试、类型检查和生产构建。

03

浏览器实测

像真实用户一样点击并操作关键路径。

第五条：没有证据，就不能说完成

这是整套流程最重要的一句话：

“No evidence，no completion。”

任务有没有完成，不看聊天里说了什么，只看磁盘上留下了什么：

规格与任务

需求、技术方案、任务状态，以及当前执行节点。

测试与审查

正式命令结果、浏览器操作证据和独立 Review 记录。

阻塞与恢复

哪些问题仍然被阻塞，以及新会话从哪里继续。

这样即使换一个新会话，AI 也能重新读取这些文件，从中断的位置继续。


04

WORKFLOW

我把这五条规矩，做成了 CM Workflow

最开始，它只是我自己使用的一组规则。后来规则越来越完整，我就把它整理成了一套可以安装的工作流。我把它叫作 CM Workflow。

CM 的意思很简单：Create More。

不是让 AI 多生成几段代码，而是让更多想法，最后真的能变成可以检查、可以测试、可以继续迭代的东西。

它目前支持 Codex，也兼容 Claude Code。你可以从一句模糊的想法开始：

我有个产品点子，先帮我梳理清楚。

AI 会先陪你把想法整理成 PRD。然后你可以说：

把这份需求拆成技术方案、开发任务和验收标准。

规格写完后，流程会停下来等你确认。你确认以后，它才开始逐个任务编码。每个任务完成后进行 Review，再运行测试，最后留下完整的交付记录。


05

TESTING

已经做完的功能，也可以重新交给它测试

这也是我自己非常需要的一个功能。很多老项目已经运行了很久，但没有完整测试用例。你甚至不知道某个功能当初是怎么设计的。

这时候可以让 CM Workflow：

1

读取现有代码，还原主要业务路径。

2

生成给 AI 使用的测试用例，检查代码逻辑。

3

运行项目正式测试命令。

4

用浏览器模拟用户操作，留下执行证据。

发现问题以后，它不会在测试过程中偷偷修改代码。它会先留下失败证据，确认问题能够复现后，再进入单独的修复流程。

测试的人负责找问题，修复的人负责改代码。两件事不会混在一起。


06

ROLE BOUNDARIES

不同的 AI，负责不同的事情

我平时主要使用 Codex 编码。需求拆分、方案讨论和复杂研究，可以使用 Claude、ChatGPT 或其他模型。

但我不希望某个外部模型拿到项目以后，既负责出方案，又负责写代码，又负责测试，最后再告诉我一切正常。

所以在 CM Workflow 里：

分析与实现

外部专家负责分析和建议；Codex 或 Claude Code 负责本地开发。

测试与审查

项目命令负责测试；浏览器验证真实路径；新上下文进行独立审查。

人的判断

规格批准、生产发布、真实资金操作、权限和密钥变更，仍然必须由人决定。

AI 可以做很多执行工作，但关键权限不能因为模型建议而自动扩大。


07

POSITIONING

它目前没有那么“宏大”

CM Workflow 现在还不是一个完整的企业研发平台。没有多租户，没有复杂的组织权限，也没有几十个 Agent 自动组建一家公司的故事。

它目前更适合：

AI 开发者

经常使用 Codex 或 Claude Code 开发真实项目的人。

一人公司

想做产品，或同时维护多个小项目的独立开发者。

中小团队

希望尝试 AI 开发，但又不敢完全相信 AI 总结的团队。

“一个需求交给 AI 以后，怎么知道它到底有没有真正完成？”

它首先解决的就是这个非常具体的问题。如果这个问题都没有解决，再多 Agent 也只是看起来热闹。

THE END

我把它开源了

CM Workflow 目前采用 MIT License。仓库在 GitHub，Codex 和 Claude Code 用户都可以安装使用。

https://github.com/kingxiaozhe/cm-workflow

Codex 用户安装

git clone https://github.com/kingxiaozhe/cm-workflow.git

cd cm-workflow

./install-codex.sh

Claude Code 用户安装

./install.sh

安装以后，新开一个会话，运行：

$cm-check

它会检查工作流入口、角色、版本和相关文件是否正确安装。如果你也在用 AI 开发真实项目，欢迎试试。

我很想知道：你最不相信 AI 的哪一句话？是“测试已经通过”？是“页面已经验证”？还是“代码已经可以提交”？因为这套工作流接下来要解决的，正是这些真实的不信任。

CM means Create More。但在 Create More 之前，我们得先让每一次“完成”，都经得起检查。
