# $cm-prd 需求倒推与逐轮追问

> 新建模式 Step 5.5 与变更模式 C4 之后读取本文件。七项倒推清单的内容以
> `../../cm-product-manager/SKILL.md` 第 2 节为准；本文件规定执行顺序、提问格式、停止条件与交接。

目标：不只核对需求文档写了什么，还要对照项目现有业务找出文档漏掉的范围，把缺口和产品逐轮
对清后再生成规格（实跑反馈：产品文档常范围不明或直接漏项，开发中途才暴露）。

## G1 合并问题清单（每次都跑）

1. **证据来源**：新建模式复用 Step 4 已加载的地图与代码，变更模式复用 C2–C4 读过的规格与代码；
   不够时按 `context-scope.md` 补读相关代码与直接调用方，不为追问另做全量扫描。
2. **倒推七项**：对需求涉及的每条业务线路逐项过七项清单。
3. **原必问项**：同时检查原 Step 5.5 的触发条件——功能点模糊或有歧义、实现方案差异大、
   缺关键信息（目标平台、兼容性、第三方服务选型）、业务逻辑矛盾或不完整、涉及权限/支付/隐私/删除等敏感操作；
   以及歧义五问、`cm-finance-expert` 合规问题、greenfield G1；微信小程序平台就绪中会改变功能可行性或范围的项
   （只影响后续提审的材料按主 Skill Step 5.5 记为发布待决，不进清单）；宿主材料阶段用户未逐项答复的原型死区（不许静默丢弃）。
   以上全部进清单，影响级按第 4 条的表判定。
4. 每个缺口记录：

   | 字段 | 写法 |
   | ---- | ---- |
   | 检查项 | 七项之一，或「范围」「成功判据」「技术选型」「合规」「平台就绪」「原型死区」 |
   | 出处 | 需求文档 `文件:行`、代码 `路径:行`、地图章节名 |
   | 影响级 | `阻断` 或 `默认`，判定见下表 |
   | 推荐答案 | 依据现有业务给出的建议；没把握时写「无推荐，需产品决定」 |

   | 影响级 | 条件 |
   | ---- | ---- |
   | `阻断` | 决定功能做不做或主流程怎么走；改变交付形态、数据结构或存量数据；涉及权限、支付、隐私、删除；实现方案差异大、缺关键信息、业务逻辑矛盾或不完整 |
   | `默认` | 只影响上限值、文案、排序、展示细节等，且有合理默认 |

5. 能从代码、地图或文档查到的事实自己查清，写进出处，不问用户。
6. 地图没有对应线路（盲区）时，用代码定向搜索作出处；本阶段只读，盲区留给 B5 在拆分前补扫。
7. 只有确认为全新项目（GREENFIELD）时才只核对文档内部缺口；存量项目缺地图时照常查代码。
8. 当前为 `CONTEXT_SCOPE=targeted` 且发现改变实现范围的缺口 → 按 `context-scope.md` 第 4 节升级。
9. 合并清单为空 → 不提问，直接进入 G4，结论记「倒推核对 7 项无缺口」。

## G2 设计树与前沿

问题按依赖排序：一题的答案会改变另一题的问法或是否需要问，后者就依赖前者。
「前沿」是依赖的题都已有答案的问题，本轮只从前沿取题。互相依赖（成环）的未答题彼此不算前置，
一起进入前沿；超过 5 题时按 G3 分到后续轮次。参考层次（同层内无依赖的题可同轮问，
下层题不依赖未决上层题时也可提前）：

1. 范围与交付形态（本期做什么、明确不做什么）
2. 角色与权限
3. 状态流转与数据（含存量数据处理）
4. 相邻线路、入口、通知、报表与导出
5. 异常、空态与文案

默认清单同样只列前沿内的 `默认` 项；依赖未决题的默认项留到之后的轮次。
某个 `阻断` 题依赖的 `默认` 项按 `阻断` 处理。
上游答案使某题不再适用时（如本期不做导出，导出权限题随之失效），该题记「不适用：{依据的答案}」移出清单，
不再计入未答 `阻断` 题，并在「范围与覆盖核对」中保留这条记录。
用户改答某题时，所有依赖它的已答题和「不适用」题都恢复为未答，按新答案重新确认。
「不适用」的题算作已解决，其他题对它的依赖随之解除。
兜底：仍有未答 `阻断` 题而前沿为空时，这些题直接进入前沿（按 G3 分轮），不得因此卡住或放行。

## G3 每轮格式

- 每轮最多 5 题，`阻断` 级优先；每题写清出处与推荐答案。
- `默认` 级不单独出题，汇成本轮末尾的「默认清单」。
- 每轮文字能原样转发给产品：不依赖前文，不写内部步骤名。第 2 轮起开头用「已记下：」复述上一轮已采纳的结论。
- 题号带轮次：第 N 轮写 `RN-Q1`、`RN-D1`，按轮次对应。回复不带轮次时：此前各轮已无未答题 → 指最近一轮；
  否则先问清指哪一轮再记录。
- 原型死区问题由宿主在分析前一次性发出（`materials` 阶段的既有行为），不受 5 题限制；
  用户逐项答复的死区作为已知事实不再重问，未答复的按 G1 第 3 条进入合并清单。

```text
❓ 第 {N} 轮需求确认（最多 5 题）

R{N}-Q1 【{检查项}】{问题}
   出处：{文档/代码/地图位置}
   推荐：{推荐答案}

R{N}-Q2 ...

默认清单（需明确回复，未提到的默认项不算同意）：
R{N}-D1 {默认做法}（出处：{位置}）

回复方式：「R{N} 全部按推荐」采纳本轮有推荐的题与默认清单；或逐题写「R{N}-Q1 是」「R{N}-Q2 否：{你的答案}」，
默认项写「R{N} 默认全同意」或「R{N}-D1 是」「R{N}-D1 否：{你的答案}」；
标「无推荐」的题请直接写答案，如「R{N}-Q3：{你的答案}」。
```

- 本轮只有一题且该题有推荐答案时，回「是」即采纳该题推荐。本轮不止一题时，单回「是」不算任何一题的答案，
  下一条消息先问清指哪几题。
- 「全部按推荐」「默认全同意」同样按上条规则对应轮次。「全部按推荐」采纳写了推荐答案的题和默认清单，
  「默认全同意」只采纳默认清单；「无推荐，需产品决定」的题必须逐题回答。
- 未提到的题和默认项都保持未答，下一轮是否再问由 G2 重算前沿决定，不按沉默视为同意。

## G4 停止、交接与记录

- **停止**：每次答复后重算前沿，前沿为空且全部 `阻断` 级已有用户答案即停止；
  `阻断` 级答完后新解锁的 `默认` 项继续出默认清单，
  直到前沿为空（用户已说「先这样」时剩余默认项记为「留待人审」）。
  用户说「先这样」时，`默认` 级未答题转为「留待人审」；仍有 `阻断` 级未答题时只继续提问这些题，
  不进入生成。超时、沉默或推荐答案都不能代替用户答案。
- **答案矛盾**：每次答复后核对已答内容与需求、现有业务之间有无矛盾；有矛盾时把它作为新的 `阻断` 题
  （检查项「业务矛盾」，出处写冲突的两条答案），解决前不满足停止条件。
- **宿主交接**：
  - 每轮返回 `{status:"question", question:"<整轮文本>"}`；用户答复经 advance 回来后重算前沿。
  - 满足「停止」条件才返回 `analyzed`（任何情况下都要求全部 `阻断` 级已有用户答案），
    `openQuestions` 必须为 `[]`（非空会让宿主停在等待）。
  - 逐条决定写进 `analyzed.summary` 的「范围与覆盖核对」段：本期做、明确不做、
    追问补齐项（检查项、出处、问题、答案或「默认」）、留待人审项。
- **写入规格**：新建模式 Step 8、变更模式 C5 读取该段，写入 `requirements.md` 的
  「范围与覆盖核对」一节，并同步受影响的功能需求与验收标准；留待人审项同时列入「开放问题」。
- **摘要卡**：Step 11 的 `openQuestions` 字符串先写一句倒推结果：
  `倒推核对：{N} 项缺口，已答 {M}，留待人审 {K}` 或 `倒推核对 7 项无缺口`。

## 变更模式

C4 影响分析之后执行 G1–G4，倒推重点放在本次变更对已有线路、已完成任务和存量数据的影响。
C5 更新「范围与覆盖核对」时保留历史条目，新条目后标注本次需求版本（如 `[v2]`）。
